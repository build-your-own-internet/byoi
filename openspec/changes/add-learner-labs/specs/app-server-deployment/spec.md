## ADDED Requirements

### Requirement: The API is served from the same origin as the content site

The deployed system SHALL serve the app's endpoints under `/api/` on the hostname the content
site already uses, routed by the `public_web` provider. The content site SHALL continue to be
served statically from `/`, and content requests SHALL NOT reach the app.

Registering a route on a hostname caddy already serves publishes no new DNS record. Same origin
also means no cross-origin configuration exists, and a configuration that does not exist cannot
be widened later by accident.

#### Scenario: An API request reaches the app

- **WHEN** a request is made to `https://<domain>/api/health`
- **THEN** the app answers it

#### Scenario: A content request is served statically

- **WHEN** a request is made to `https://<domain>/` or to any chapter page
- **THEN** the static file is served without involving the app

#### Scenario: Content survives the app being down

- **WHEN** the app is stopped
- **THEN** every chapter page still serves

#### Scenario: The profile page degrades rather than hangs

- **WHEN** the app is unreachable and a person opens the profile page
- **THEN** the page renders an explicit failure state rather than waiting indefinitely

#### Scenario: No new public record is published

- **WHEN** the module is deployed
- **THEN** the only public DNS record for this site is the one that already existed

### Requirement: The app has no public listener of its own

The app SHALL sit in the `app` zone and listen on its zone address, reachable from the reverse
proxy in `dmz`. It SHALL have no public port, no DNAT rule, and no DNS record of its own.

It listens on its zone address rather than only on loopback because the control plane calls it
directly rather than through the proxy, so that provisioning does not depend on the proxy's
health as well as the app's.

#### Scenario: The app is unreachable from outside

- **WHEN** the app's host and port are probed from outside the perimeter
- **THEN** the connection is refused or dropped

#### Scenario: The control plane reaches it directly

- **WHEN** the reconcile hook calls the app at its zone address
- **THEN** the app answers, without the request passing through the reverse proxy

### Requirement: The app holds no infrastructure credential

The app SHALL hold no credential for the hypervisor, the firewall, the address manager, or
celilo, and SHALL make no outbound call to any of them.

This is the bright line. Compromising the data plane must not yield the control plane.

#### Scenario: No infrastructure credential is present

- **WHEN** the app's configuration and secrets are examined
- **THEN** none is a credential for the hypervisor, the firewall, the address manager, or celilo

#### Scenario: The app makes no call to infrastructure

- **WHEN** a person requests and releases a lab
- **THEN** the app makes no network call to any hypervisor, firewall, or address manager

### Requirement: The control plane authenticates to the app with its own credential

The reconcile surface SHALL require a bearer credential distinct from any person's session,
generated by celilo rather than chosen by an operator, and compared in constant time. That
credential SHALL NOT be usable on the browser surface, and a session SHALL NOT be usable on the
reconcile surface.

#### Scenario: The reconcile surface refuses a person's session

- **WHEN** a caller presents a valid person's session cookie to the reconcile surface
- **THEN** the request is refused

#### Scenario: The browser surface refuses the reconcile credential

- **WHEN** a caller presents the reconcile credential to the browser surface
- **THEN** the request is refused

#### Scenario: A wrong credential is refused without leaking timing

- **WHEN** an incorrect reconcile credential is presented
- **THEN** the request is refused, and the comparison does not reveal how much of the credential was correct

### Requirement: The app reports its own health and whether it has converged

The module SHALL expose a health check that fails when the app cannot serve requests or cannot
query its database, and that reports how many labs are awaiting provision or destruction.

A count that never reaches zero means the control plane is not converging, and that is the
symptom an operator needs to see.

#### Scenario: A working deployment reports healthy

- **WHEN** the health check runs against a working deployment with nothing pending
- **THEN** it reports healthy and reports zero awaiting provision and zero awaiting destruction

#### Scenario: An unreachable database is unhealthy

- **WHEN** the database cannot be opened or queried
- **THEN** the health check reports unhealthy

#### Scenario: A stalled reconcile is visible

- **WHEN** labs have been awaiting provision across several intervals
- **THEN** the health check reports the counts rather than reporting healthy

### Requirement: Data survives redeployment

The database SHALL live outside the artifact the publish step replaces. Schema migrations SHALL
run when the app starts, so that an upgrade which restarts the app also migrates it.

An upgrade path that does not run migrations leaves the app running against an old schema, and
the failure is silent until something touches a column that is not there.

#### Scenario: A redeploy preserves records

- **WHEN** user and lab records exist and the module is redeployed
- **THEN** the records are still there and still associated with the same people

#### Scenario: A deploy carrying a migration applies it

- **WHEN** a version carrying a pending migration is deployed and the app restarts
- **THEN** the migration has been applied without anyone running a hook by hand

### Requirement: An account exists for the end-to-end login gate

The module's install SHALL provision an account in the identity provider with a celilo-generated
password held as a declared secret, so that the end-to-end suite signs in through the real login
flow. The deploy SHALL refuse without that secret.

A gate that only asserts the page rendered is not a gate. An account whose password nothing
knows cannot be signed in as, so the password is generated and stored rather than discarded.

#### Scenario: Install provisions the account

- **WHEN** the module is installed
- **THEN** the account exists with the generated password, and an operator can read it back with `celilo module secret get`

#### Scenario: A missing secret stops the deploy

- **WHEN** the module is deployed with no generated password secret
- **THEN** the deploy fails rather than proceeding with an account nobody can sign in as

### Requirement: The deployed stack is proven end to end

This change SHALL be gated by tests that drive a real deployed stack, meaning the identity
provider, the reverse proxy, the app, and the control plane together. Unit-level checks SHALL
NOT count as evidence, because the failures being guarded against are deployment mistakes.

#### Scenario: A real sign-in works

- **WHEN** the suite signs in as the provisioned account through the real login flow
- **THEN** it receives a session and can read its own identity

#### Scenario: A whole lab lifecycle works

- **WHEN** the suite requests a lab, runs the reconcile hook, and waits for it to become ready
- **THEN** the lab exists, is reachable on its assigned port with the submitted key, and reports an address, port, and host key fingerprint

#### Scenario: Releasing a lab destroys it

- **WHEN** the suite releases the lab and runs the reconcile hook
- **THEN** the container is gone and its port forward no longer reaches anything

#### Scenario: A forged credential is refused

- **WHEN** the suite calls the API with a session identifier it invented and with a token the deployed provider did not sign
- **THEN** both are refused

#### Scenario: A forwarded-user header is refused

- **WHEN** the suite calls the API with a header naming a user and no valid session
- **THEN** the request is refused
